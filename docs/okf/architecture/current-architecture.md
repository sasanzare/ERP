# Local Runtime Architecture

## Implementation state

The Laravel 13 application and P01 source/configuration are at the repository root. Composer and npm dependencies are locked and installed. P01–P12 are accepted at their local-development boundaries after validating migrations, repeatable provisioning, browser/API paths, and Persian RTL workspaces. P11's local read-only dashboard and repeatable synthetic walkthrough passed focused and full guarded suites plus Chrome responsive/fallback acceptance. P12 adds organization-scoped project work and P08 purchase-line cost trace; its focused suite passed 7 tests / 133 assertions and the full guarded suite passed 97 / 1,216. P10 approval is limited to the local synthetic ERP MVP; live/production posting remains disabled. P06 includes an immutable stock ledger, location balances/reservations, and concurrency controls. P07 connects confirmed order lines to those reservations and issues with partial delivery, cancellation, and operation/movement traceability. P08 adds independent purchase approval, supplier-order price snapshots, and atomic partial inbound receipts. P09 adds a manual balanced-journal engine with books, accounts, periods, retries, closures, and reversals. P03 session, organization, membership, policy, and audit behavior remain the authorization base.

## Implemented P01 topology

- Laravel Framework 13.43.0 serves the Blade browser entry and `/api/v1/products` from host-side PHP 8.5.13.
- React 19.3.1, TypeScript 5.9.3, and Vite 8.3.8 sources live under `resources/js/`; Vite serves development assets and hot reload.
- `npm run dev` runs `scripts/Run-LocalDev.mjs`, which starts Laravel's loopback server on port 8000 and Vite on port 5173, forwards Ctrl+C to both, and leaves Docker/MariaDB lifecycle to the developer. `ERP_PHP_BINARY` can select the host PHP executable; the default is `C:\php8.5\php.exe`.
- The product API serializes `id`, `code`, and Persian `name` from the Eloquent Product model backed by MariaDB.
- MariaDB is configured as Compose service `db` with image `mariadb:11.8.9-noble`, a health check, and persistent volume `erp_mariadb_data`.
- Host PHP uses loopback and configurable `DB_FORWARD_PORT` defaulting to 3307; container port is 3306.
- Compose initializes development schema/user `erp_dev`/`erp_app`; an idempotent init script creates test schema/user `erp_test`/`erp_test`. Each account is scoped to its own schema.
- Before Laravel's `RefreshDatabase` trait runs, the shared test case validates `APP_ENV`, MariaDB driver, loopback host, matching local port, exact `erp_test` database/user, and absence of URL/socket overrides. A non-destructive unit test verifies that `erp_dev` is rejected.
- The React product surface uses the Liquid Glass template's measured inverse-lens displacement map, geometry-based caching, a solid/tinted reduced-transparency fallback, and reduced-motion/contrast handling. Query `?glass=fallback` forces the fallback for visual QA.
- The P02 React shell serves `/`, `/products`, and numeric `/products/{id}` entry paths. It keeps `GET /api/v1/products` and its `{id, code, name}` record fields unchanged; list filtering and detail selection happen client-side. See [the P02 workspace architecture](ui-workspace.md) and [UI design reference](../../UI_DESIGN.md).
- P03 protects browser workspace routes with Laravel session authentication and redirects guests to `/sign-in`. API workspace routes add the `web` middleware group for sessions and apply an explicit token check to state-changing requests.
- The organization and product migrations backfill existing products to `legacy-local` (`سازمان پیش‌فرض`) before making `organization_id` required; product code uniqueness is scoped to organization. The forward migrations were applied to the existing local database, and product ID 1 was preserved.
- P03 organization context is resolved from current user memberships on each protected request. Product listing and numeric-ID update queries are organization-scoped, and the product policy permits updates only for the `editor` membership role.
- P04 migration `2026_11_20_000005_create_p04_master_data_tables` adds parties/roles, units, warehouses, locations, price lists/entries, and an optional product base unit. Existing product IDs, owners, codes, and names were read before and after the `erp_dev` migration and remained unchanged. Unknown legacy units stay `NULL`.
- P04 API controllers scope reads, writes, filters, and relationships to the active organization. Composite foreign keys protect product units, location warehouses, party roles, and list entries. `OrganizationPolicy` permits readers to view and editors to manage master data.
- P04 React routes use one shared register/form pattern for `/parties`, `/units`, `/warehouses`, `/locations`, and `/price-lists`; the existing `/products` route keeps its collection response and adds product create/base-unit editing. Selected-list price resolution is a dedicated endpoint and exact rial amounts are returned as strings.
- The existing `p03:provision-demo` command also provisions repeatable P04 fixtures. On `erp_dev`, two consecutive runs retained 2 organizations, 3 memberships, 3 role-audit rows, 3 products, 1 party with 2 roles, 3 units across two organizations, 2 warehouses, 2 locations, 2 price lists, and 2 price entries.
- P05 adds organization-scoped leads, activities, quotes, and confirmed orders. P04 prices remain exact rials while P05 document snapshots use integer tenths of a toman and thousandth-unit quantities; quote conversion is transactional and idempotent.
- P06 adds `inventory_operations`, immutable `inventory_movements`, `stock_reservations`, and a unique `(organization_id, product_id, location_id)` `stock_locks` registry. Balances are derived from inbound/outbound legs and open reservations. The local dev migration is applied and the accepted fixtures keep product IDs/units 1–5 unchanged.
- The P06 workspace uses `/stock`, `/stock/movements`, and `/stock/reservations`; API writes require an editor role, explicit CSRF, and organization-unique idempotency UUID. MariaDB writers lock product and location rows plus sorted stock-key rows.
- P07 migration `2026_11_21_000008_add_p07_sales_fulfillment` adds reservation ownership/counters, line cancellation state, a delivery trace table, and operation/movement keys. Sales fulfillment locks the order line before following the P06 product/location/stock-key/reservation order. Delivery posts one outbound issue and delivery trace atomically; cancellation releases the unfulfilled reservation remainder without a movement. P06 standalone release rejects line-managed reservations.
- P08 migration `2026_11_21_000009_create_p08_purchase_tables` adds organization-scoped request, request-line, order, order-line, and receipt records. One approved request converts to at most one order; source-line product/unit/quantity and supplier/price/total values are saved as historical snapshots. Purchase prices are whole IRR per base unit; each line rounds half-up once to whole rials and the order total sums the rounded lines.
- The P08 workspace is `/purchase-requests` and `/purchase-orders`. A requester cannot approve their own request. Receipt submission derives product/unit from the saved order line, adds an optional source scope to the P06 operation hash, and locks order → line → product → warehouse/location → stock key. A final unit/outstanding check, P06 inbound operation/movement, receipt link, received counter, and order closeout commit atomically. P06 standalone receipt remains available.

## Implemented P09 accounting

- Migrations `2026_11_22_000010_create_p09_accounting_tables` and `2026_11_22_000011_add_p09_one_sided_line_amount_check` add organization-owned books/accounts/periods, journals/lines, and request-key records. Composite foreign keys keep accounts, periods, journals, reversals, and retry keys within one organization and book. A MariaDB CHECK enforces one positive debit or credit per line.
- The workspace is `/accounting/journals`, with `/accounting/journals/new` and `/accounting/journals/{id}` for draft entry and review. Editors set up books, accounts, and non-overlapping inclusive Gregorian periods; readers can review. Periods record an IANA timezone (local default `Asia/Tehran`), and accounting dates are date-only.
- Posting requires a nonzero exact balance, active postable same-book accounts, and exactly one open period. Book-first transaction locks serialize posting, period creation/closure, and reversal. Successful posting/reversal keys return persisted records after closure; one unique original relation prevents a second reversal. Posted headers/lines have no update/delete route.
- P09 stores whole-rial amounts and emits exact decimal strings. P05 Toman snapshots convert by exact ×10 only when explicitly selected; P08 purchase snapshots remain rials. Existing P05/P06/P07/P08 workflows do not post automatically. The internal P10 action requires callers to resolve source records in the active organization. Only the local workflow approved in [ADR-008](../decisions/adr-008-p09-accounting-scope-and-posting-decisions.md) is enabled; live/production source posting remains gated.

## Implemented P10 settlement boundary

- Migration `2026_11_24_000012_create_p10_settlement_tables` adds organization/book-scoped accounting profiles, customer/supplier invoices and lines, open items, treasury movements, and allocations. It also adds unique source-trace indexes on P07 deliveries and P08 receipts. It is applied to `erp_test` and `erp_dev`; exact observed P01–P09 row counts matched before/after on `erp_dev`, and the new P10 tables were empty before the synthetic Chrome walkthrough.
- `/settlements` provides customer and supplier invoice registers, source delivery/receipt selection, receipt/payment actions, outstanding balances, and links to P05/P08 sources, P07/P08 inventory traces, treasury movements, and P09 journals.
- Invoice posting creates the P10 invoice lines, balanced `p10.*` P09 journal, and open item in one transaction. Settlement locks the invoice/open item and writes the treasury movement, linked journal, and full single-invoice allocation atomically. Amounts are whole Rial; P05 Toman snapshots convert by exact ×10.
- The approved local MVP uses the existing `synthetic_test` profile for organization 1 and book 2 (`P10-SYNTH-BROWSER`); exact account IDs/codes are in ADR-008. It allows only explicit invoices over delivered/received quantities, zero-tax local amounts, and one-movement/one-invoice allocations. The profile was not changed. A live profile still requires a separate approval reference, actor, and timestamp; no application route activates one.
- P10 journals use `p10.*` source types and standalone P09 reversal rejects them. The local MVP has no coordinated correction/void route; new posting into a closed period is rejected while exact-key replay remains allowed. P11 can query posted invoices by book/organization/effective date and subtract allocations whose linked treasury journal is posted and whose treasury effective date is on or before the report date; due dates remain available for aging.

## Implemented P11 reporting boundary

- `/dashboard` is a Persian RTL, read-only workspace. The `/api/v1/dashboard/options`, `/api/v1/dashboard`, and `/api/v1/dashboard/metrics/{metric}` endpoints derive organization scope from the authenticated active membership and reject foreign accounting books with 404.
- Net sales and overdue receivables are scoped to the selected book. They use posted customer P10 invoices and posted P09 journals. Overdue residuals subtract only customer allocations with a treasury effective date through the cutoff and a posted settlement journal. Supplier invoices, drafts, standalone P09 journals, and unsupported correction/void assumptions are excluded.
- Available stock and pending approvals are organization-wide. Stock uses movement `created_at`, reservation `created_at`/`released_at`, and P07 delivery `created_at` timestamps to reconstruct availability as of an inclusive 23:59:59 cutoff in the selected book timezone. Approval history uses `submitted_at` and `approved_at` at the same cutoff. Stock totals are grouped by unit.
- Dashboard money remains exact Rial strings; Toman conversion is exact `/ 10` with a fractional digit when applicable. Source rows use server-side 25-row pages while reconciliation totals cover the full population.
- `p11:provision-walkthrough` reuses the existing organization 1 / book 2 `P10-SYNTH-BROWSER` `synthetic_test` profile on `erp_dev`. Read-only verification confirmed the profile and account mapping remain unchanged. The command uses stable business identities and P06/P07/P08/P10 idempotency keys. It is restricted to local `erp_dev` or guarded `erp_test` and does not alter the profile or existing manual journals.
- The focused guarded P11 suite passed 5 tests / 122 assertions and the full guarded suite passed 90 tests / 1,083 assertions. Chrome acceptance on 2026-11-26 matched independent local source-row totals: 5,000,000 IRR sales, 600,000 IRR overdue, 131.500 EA across 15 product/location rows, and 1 pending approval. Date boundaries, a second same-organization book, drill-downs, Toman display, loading/error/empty states, both source journeys, desktop/mobile/bright fallback, keyboard focus, and live Vite `dashboard.css` passed with zero browser errors. TypeScript, production build, changed-file Pint, Node syntax, and `git diff --check` passed. See [P11 architecture details](p11-dashboard.md), [P11 data](../data/p11-reporting.md), [P11 security](../security/p11-reporting.md), and the [handoff](../../../HANDOFF.md).

## Implemented P12 project-work boundary

P12 adds organization-owned projects, nested tasks, project/task text comments, a session-user inbox, local due reminders, and one-to-one project purchase-line links. `viewWork` gives members read access; `manageWork` restricts writes to editors. Assignees must be active-organization members. Reminder processing is an explicit CSRF-protected local POST invoked on inbox entry; a persistent identity and unique database key deduplicate refreshes and retries. The date-only due cutoff follows `config('app.timezone')`, currently UTC. P12 links an eligible P08 purchase line by stable source IDs and snapshots the exact whole-rial line total without modifying P08, P09, or P10.

Migration `2026_11_26_000013_create_project_work_tables` was applied forward to guarded `erp_test` and local `erp_dev`. The full guarded suite passed 97 tests / 1,216 assertions. Read-only development counts for organizations, memberships, P08 orders/lines, P10 invoices, and P09 journals matched their pre-migration values; the existing P11 purchase line 9 remained 500,000 IRR. Chrome verified the assigned-editor inbox/completion journey, reminder retry, board/list reconciliation, and purchase-line source link at desktop/mobile/bright fallback with visible keyboard focus, live Vite CSS, and zero runtime errors. See [P12 architecture](p12-project-work.md), [P12 data](../data/p12-project-work.md), [P12 security](../security/p12-project-work.md), and [P12 UI evidence](../../UI_DESIGN.md#p12-projects-and-assigned-work-evidence).
